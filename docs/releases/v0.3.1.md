# THALIA v0.3.1

Publication-integrity patch dated 2026-11-09 UTC. This release supersedes the
v0.3.0 supplemental-artifact defect; it does not retag v0.3.0, replace its
assets, or rerun the measured local study. The v0.3.0 feature and historical
execution description remains in [its release notes](v0.3.0.md).

## Root cause and ownership

During canonical handoff, the native renderer's generic output scan overwrote
THALIA's `output/reports/artifact_manifest.json`. That scan could not replace
the project-specific contract: it omitted the required committed
`data/integrity_advantage.json` outside `output/` and captured QA/preview
entries that were subsequently changed or omitted from the supplement. A native
working-tree pass did not qualify the final downloadable closure.

The patch separates the owners:

- THALIA writes and validates
  `output/reports/thalia_artifact_manifest.json`, including its required
  committed integrity aggregate and stable output inventory.
- The native pipeline continues to own
  `output/reports/artifact_manifest.json`; it must not overwrite or stand in for
  THALIA's inventory.
- The downloadable release manifest records source identity, actual check
  observations, and asset sizes/digests independently of both inventories.

The source adapter `scripts/render_pdf_external.py` now accepts
`--template-root PATH` to select a provisioned renderer checkout explicitly and
`--validate-only` to invoke real native validation without hydration or
rerendering. An invalid THALIA manifest fails the adapter even if native
validation succeeds. This is not a relaxation of the native or project gates.
The adapter retains the stable project identity `thalia` when a source archive
is extracted into a versioned directory, so retained publication filenames do
not change with the staging folder name.

## Final qualification and packaging

Finish all source/documentation edits, rendering, browser inspection, QA reports,
and preview selection first. Assemble a clean stage from the exact release
source plus only the supplemental allowlist, preserving relative paths and the
committed inputs supplied by the source archive. Freeze THALIA's manifest there,
run native validation-only there, then run the full project artifact gate after
native validation. Package those exact verified bytes, not a worktree that is
pruned afterward.

For an already assembled staging root, use provisioned external runtimes and
absolute paths as described in [artifact assembly](../release_artifacts.md):

```bash
set -e
cd "${THALIA_STAGE:?Set the clean staged project root}"
: "${THALIA_PYTHON:?Set the provisioned THALIA interpreter}"
: "${TEMPLATE_ROOT:?Set the provisioned template checkout}"
"$THALIA_PYTHON" -c \
  'from src.provenance import write_artifact_manifest; print(write_artifact_manifest())'
uv run --no-sync --project "$TEMPLATE_ROOT" python \
  scripts/render_pdf_external.py --template-root "$TEMPLATE_ROOT" \
  --validate-only
"$THALIA_PYTHON" scripts/validate_artifacts.py
```

Do not change manifest-tracked QA, previews, manuscript, figures, data, or
verification summaries after this final sequence. Native validation may write
its independently owned diagnostics, not rewrite frozen THALIA evidence. A
tracked change or revised allowlist requires repeating the final inventory,
native validation, and project gate. Never reseal measured study JSON to repair
a release inventory. No subsequent render, dashboard build, or QA annotation may
silently invalidate the qualified closure.
