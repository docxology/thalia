# THALIA v0.3.0

A method-aware research release: compare context methods within explicitly
selected local or consented cloud backends, with matched examples, accountable
failures, and descriptive seed-level analysis. GitHub publication is not
scientific claim promotion. No new DOI is assigned; the v0.1.0 archive retains
its own historical DOI and the v0.2.0 release remains immutable.

## Methods and execution

- `full_context`: submit the entire synthetic session through the same typed
  Reasoner signature renderer, without Inspector or Retriever selection.
- `harness`: the configured Inspector/Retriever/Reasoner path.
- `lexical_only`: disable the semantic **scoring lane**. Independently enabled
  query expansion and MMR retain their configured behavior.
- `adaptive`: enable the harness's adaptive context windows.
- Compose additional named harness configurations with `BenchmarkMethod`.
  Verifier re-answering is rejected in this one-completion benchmark.

Every backend/method/example cell submits exactly one completion unless it
fails before submission. There are no retries, warmups, or answer caches.
Backends run sequentially to avoid model thrashing; method order rotates by
example. Cohorts balance categories and rotate seed order before a global limit
is applied. Prompt hashes are compared across backends **within one method and
example**, not between context methods that deliberately submit different text.

The default remains one extractive backend and one `harness` method; choosing
additional methods or models is explicit. `--num-ctx` records a requested
Ollama context size, not proof that a provider retained every input token.

## Analysis and visible evidence

Schema 2 records methods/configuration fingerprints, seed-aware example identity,
execution indices, prompt characters, answers, token F1, observed end-to-end
latency, and safe exception classes. It separates backend metadata from
per-method summaries and includes category/stratum diagnostics. Portable source
inventories and observed runtime/dependency metadata help detect producer drift;
checksums are not execution authentication or provider-binary attestations.

Paired contrasts compare methods on the same example within the same backend.
The estimand is the unweighted mean of per-seed mean token-F1 differences, not a
mixed-backend score. Any incomplete pair suppresses the contrast estimate and
interval. One represented seed suppresses the interval. With multiple seeds,
the interval resamples seed means and remains descriptive; small-cluster
warnings are mandatory. No p-values, power claims, expert correctness labels,
or general model rankings are produced.

The dashboard and hydrated manuscript expose observation and contrast tables,
accounted failures, reference-absent states, and the finite-cohort limitations.
A registered method-design diagram explains execution and analysis dependencies
without duplicating the numeric tables as a chart.

## API and artifact migration

```python
from src.evaluation.backend_benchmark import (
    build_benchmark_backends,
    build_benchmark_methods,
    run_backend_benchmark,
)

report = run_backend_benchmark(
    build_benchmark_backends(),
    methods=build_benchmark_methods(("full_context", "harness")),
    per_category=1,
    seeds=(0, 1),
)
```

- Pass base configuration to `build_benchmark_methods(config=...)`, not to
  `run_backend_benchmark`.
- Use plural `seeds=(...)` in the API; repeat `--seed` on the CLI.
- Read `summaries` by backend **and method**; `backends` is metadata only.
- Schema-1 reports are rejected rather than guessed into a method-aware matrix.
  Preserve their versioned reader or execute a new schema-2 study. Renaming
  fields cannot recover unmeasured methods, seeds, prompts, or provenance.
- `scripts/z_generate_manuscript_variables.py --benchmark-report PATH` explicitly
  selects a complete or incomplete current report for honest publication.
  Incomplete runs preserve the last complete destination and write a diagnostic
  sidecar; selection never promotes failed observations to successes.

## Reproduction and scope

See [the benchmark API and CLI guide](../backend_benchmark.md),
[the declared local method study](../local_method_study.md),
[publication gates](../release_readiness.md), and
[artifact assembly/download verification](../release_artifacts.md).

Prompt characters are not billed tokens. End-to-end method latency includes
context processing and client/provider behavior; it is neither throughput nor
cost, and the host is not a controlled hardware laboratory. Token overlap can
penalize verbosity and does not establish entailment or expert answer quality.
Historical DSPy/cloud observations remain separate from the matched method
study. Independent P0 confirmation, expert-rater quality, and production
acceptance remain unexecuted unless their own protocols supply evidence.

## Observed local execution

The declared study completed on 2026-11-08: **1,152/1,152 cells, zero failures**,
including **864 real Ollama responses** across `gemma3:1b`, `gemma2:2b`, and
`gemma3:12b`, plus 288 extractive responses. All four methods used the same
72 example IDs and three seed cohorts; no row, model, or method was replaced
or retried. The full receipt and statistical-validity review are in
[`local_method_study.md`](../local_method_study.md).

Results do not show a uniform harness benefit. The harness/full-context contrast
was positive for the selected 1B model, negative for the selected 2B model, and
changed sign across seeds for the selected 12B model. Adaptive and ordinary
harness submitted identical per-example prompts on this cohort. The 72 IDs
contain 54 distinct full-context inputs, and the longest submitted prompt was
1,655 Unicode characters: this is not an advertised-window-capacity stress test.
Every contrast retains its three-seed descriptive warning.

The final readers expose repeated inputs and exact per-example prompt-policy
groups rather than presenting nominal method labels as independent quality
evidence. These post-run diagnostics do not alter the primary measured rows.
The exact original producer wheel, its Git source snapshot, and all observed
software dependency versions are retained in the supplement's `STUDY_PRODUCER/`
capsule; they remain distinct from the final reader wheel.
